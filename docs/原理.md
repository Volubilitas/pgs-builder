# 原理：从 ASS 到 PGS 位流

> 本文只讲**为什么这么做**。每一步的代码在 `gen_pgs.py` / `pgsenc.py`，坑的清单在 `坑.md`。

## 0. 问题的形状

PGS（HDMV 位图字幕）一条轨 = 一张 **256 项调色板**（每项 `索引, Y, Cr, Cb, T`）+ 一张**调色板索引位图**（RLE 压缩）
+ 一串 **display set**（每个 set 说明"这一帧把哪个对象摆在画面哪个位置"）。

输入是矢量/文字（ASS），必须先**渲染成像素**才能量化。ffmpeg 能渲染（libass），但**没有 PGS 编码器**
（见 README 开篇的实测），所以本工程只干"渲染之后"的那一段：两趟渲染 → 反解 (c, α) → 建板 → 量化 → RLE → 写段。

## 1. 为什么要两趟黑白渲染（全工程最关键的一步）

播放器合成字幕用的是：

```
out = src·(1 − α) + c·α
```

**ASS 渲染器给的 α 通道不是这个 α。** 直接拿 `ass=...,alpha=1` 输出的 alpha 通道，实测只有真实 α 的
**63%**（各 α 档一致落在 58~65%）⇒ 整条字幕被系统性压暗到 2/3，而"整帧 RMSE"看不出来。

正确做法是同一帧渲两遍，底色不同：

```
黑底  B = c·α
白底  W = 255·(1−α) + c·α
⇒ α = 1 − (W − B)/255        c = B / α
```

拿第三张**灰底**渲染独立验证：预测/实测 = **99.8%**。代码就是 `gen_pgs.solve_ca()`；两趟渲染进程同时读，
帧号一一对应，不落盘任何中间帧。

## 2. 为什么一切都在「预乘空间」里做

- PGS 存的 `(c, α)` 在播出时是 **`c·α` 参与加法**（见 §1），所以量化误差必须按 `c·α` 来算，不能按直乘的 `c`。
- 特征向量取 `(c_r·α, c_g·α, c_b·α, α·WA)`，`WA = 1.0`：因为播出误差里含 `255·Δα` 这一项，
  **α 维度必须与颜色维度同权**，否则淡部的 α 会被牺牲掉换颜色精度。
- 若在直乘空间找最近邻，"明亮但 α 很小"的格子会抢走淡部像素 ⇒ 淡部整片发闷、层次塌成几档。

## 3. 调色板：按这条字幕**自己的内容**建

PGS 只有 256 个槽，其中索引 0 固定为"全透明" ⇒ 实际可用 **255 色**。半透明淡部（α≈2~60）又要占掉大量档位，
所以调色板必须按内容自适应：

1. **抽样**：每 `--step` 秒取一帧（抽样在 Python 侧做，不用 ffmpeg 的 `select`，见坑 5）；
2. **收集**：两趟黑白渲染反解出 (c, α)，取 `α ≥ AL_MIN` 的像素，打包成整数直方图（颜色 → 出现次数）；
3. **中值切分**：在 4 维预乘特征上做 median cut，切成 255 个盒子，取质心；
4. **反预乘**：`c = P/(α/255)`，存成 `.npy`（`(255,4)` uint8）。

参数取舍：

- `AL_MIN = 2`：淡粒子与抗锯齿边缘的主力正好落在 α 2~30，砍掉就等于把"雾"砍掉。
- `FAINT_BOOST`（低 α 计数加权）**默认 1.0，别乱开**：>1 会把中值切分的质心往淡端拽，亮像素被映射到偏暗的格子
  ⇒ 亮端整体被压暗（实测某帧亮像素 `PGS/源 = 0.67`，跨整个亮度档是一条平线）。淡端分级靠 `AL_MIN` + 预乘空间已经够。
- `--step`（**抽样密度**）是最影响往返误差、却几乎不花体积的一个参数：同一条示例、同一块画布，
  1.0 s（默认）→ RMSE **8.670**（过不了判据），0.05 s → **1.556**，0.02 s → **1.252**，
  而 `.sup` 只从 4.69 MB 变到 4.76 MB ⇒ **按内容显式给，别吃默认**（完整曲线见 README，坑 21）。
- 效果：示例里那条 **12 档 α 阶梯**，在解码帧里还原出 **143 个不同的 α 值**，最高 α=246 —— 淡部是真被铺开了。

## 4. 逐帧编码：量化 → RLE → display set

```
每帧：
  两趟渲染 → solve_ca → 取 α≥AL_MIN 的 bbox（外扩 MARGIN=8）
  → 只在这块里做预乘空间最近邻（分块 4096，避免大矩阵）→ 索引图
  → RLE（每行写满宽度）→ display set（PCS/WDS/PDS/ODS/END）
```

- **对象窗口**：按内容 bbox 裁，写进 WDS 的 `(x, y, w, h)`，坐标要加回渲染窗口偏移 `(CX+x0, CY+y0)`；
  `--crop` 让 ffmpeg 只渲染内容所在窗口，是全片提速的主要手段。
- **没有内容的帧**：若上一帧有内容，就发一个 `n_obj = 0` 的空 display set 把画面擦掉（否则上一张字幕会一直挂着）。
  片尾也补一个。
- **PTS**：90 kHz 时钟。`--abs-pts` 用绝对时间轴（从 `t0` 起算），默认相对（第 0 帧 = 0）。
  相对 PTS 的分段 `.sup` 不能直接拼。
- **PCS 的 composition_state**：
  - `0x80` epoch start（**首个** set）；
  - `0x00` normal（其余全部）——本工程的每个 set 都自带完整调色板和唯一对象，**本 set 就是完整合成**；
  - ⚠️ 绝不能用 `0x40` acquisition point：解码器会保留上一帧的对象再叠加 ⇒ 细颗粒出现灰色拖影
    （实测解码帧像素数正好翻倍）。
- 每个 set 重发完整调色板（1282 B / set）是**故意的**：不依赖"调色板复用 / 窗口复用"这类高级特性，
  换来任何解码器都认。代价见 README 的"已知限制"。

## 5. RLE 的两条硬规矩

1. **EOL 只推进行号，不补像素。** ffmpeg 的 `decode_rle` 用全局 `pixel_count` 校验，要求显式写出的像素总数
   正好等于 `w × h` ⇒ **每一行（含全透明行）都必须写满对象宽度**，行尾透明像素并入最后一个游程；
   否则解码器报 `Insufficient RLE data`。
2. 四种游程形式（单像素 / 短游程 / 14 位长游程，颜色 0 与颜色 C 各一套）：
   ```
   CC                     单像素，颜色 C
   00 0LLLLLL             L 个颜色 0
   00 01LLLLLL LL         14 位长度，颜色 0
   00 10LLLLLL C          L 个颜色 C
   00 11LLLLLL LL C       14 位长度，颜色 C
   ```
   实现见 `pgsenc.rle_row()`。

## 6. ODS 分片与 16 位段长

ODS 的 body 长度 = `4(对象头) + 3(对象数据长度字段) + 4(w,h) + len(rle)` = **`len(rle) + 11`**，
而段长字段只有 **16 位** ⇒ 判据必须是 `len(rle) + 11 ≤ 65535`。
用 `len(rle) + 4` 当判据，会让 `len(rle) ∈ [65525, 65531]` 落进"不切片"分支，`struct.pack('>H')` 当场
`struct.error`（实测全片跑到第 12240 帧炸）。修复后切片分支每片 body ≤ 65008，安全。

**这条路径在 4K 上真的会走到**：4K60 示例 300 帧实测 ODS 段 **215** 个 vs PCS **121** 个 ⇒ 触发了 95 次分片。

## 7. 颜色空间

调色板项 = `(索引, Y, Cr, Cb, T)`，**BT.709 有限范围**（Y 16~235、Cr/Cb 16~240），`T` 直接就是 α。
解码时用同一套系数反变换（`sup解码.ycc_to_rgb`）—— 这也是往返验收能对齐到 RMSE 3.8 的前提。

## 8. 吞吐的真相：代价由「覆盖像素 × 每帧独特色数」决定

热点是 Python 侧的"每帧唯一颜色 → 调色板最近邻"映射，与画布大小只有间接关系：

| 场景 | 字幕覆盖率 | 实测吞吐 |
|---|---|---|
| 1920×1080 示例（窗口 1400×800，密图形） | ~40% | **~10 帧/秒** |
| 3840×2160 示例（窗口 3840×1638，密图形） | ~20% | **2.2 帧/秒** |
| 3840×1638 真实全片（稀疏粒子） | 0.16% | **13.2 帧/秒** |

⇒ 拿一个 4K 密图形 demo 去估真实字幕轨的耗时，会**高估 6 倍**；反过来也一样。

## 9. 与其它做法相比

- **位图字幕不随分辨率缩放**：换输出尺寸必须重编 —— 这也是"先定死分辨率再编"的原因。
- 想省体积可以只在调色板变化时发 PDS、或复用窗口定义；这些"高级特性"没在电视上验证过，
  本工程选了最保守的写法（每 set 全量）。要省体积，先改这两处，再拿 `验收PGS.py` 复验一遍。
